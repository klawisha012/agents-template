# Шаблон: GitHub Projects + агенты

Это шаблон для GitHub-репозитория: 27 скиллов Matt Pocock в `.agents/skills`, общие инструкции и распределитель GitHub Issues по ролям команды. Поддерживаются Codex, Cursor и Claude Code. В исходном шаблоне нет состава команды. Термины процесса описаны в `GLOSSARY.md`.

## Как перенести

1. Создайте репозиторий из этого шаблона или скопируйте в существующий `.agents/`, `.claude/`, `.github/workflows/distribute.yml`, `.github/workflows/close-parents.yml`, `AGENTS.md`, `CLAUDE.md`, `GLOSSARY.md` и `docs/adr/`. При желании добавьте `tests/`. Если файлы уже есть, сначала объедините их, сохранив существующие инструкции и настройки.
2. На компьютере, где публикуются тикеты, нужны Python 3 и установленный GitHub CLI (`gh`). Выполните `gh auth login`; у аккаунта должны быть права создавать и читать issues. Подключение агентов к GitHub само по себе не заменяет `gh` для этого процесса.
3. Скопируйте `.agents/team.example.json` в `.agents/team.json`. Укажите настоящий `OWNER/REPOSITORY`, справочник ролей `roles` (название роли и её описание) и участников: GitHub-логин, `roles` из справочника и относительную `capacity` (по умолчанию 1). У участника может быть несколько ролей; участник без ролей получает только тикеты без роли. Не добавляйте токены в JSON. Каждый участник должен иметь право быть назначенным на issue в этом репозитории.
4. Откройте репозиторий в своём агенте и выполните `/setup-matt-pocock-skills`: выберите GitHub Issues и настройте документацию трекера и метки. Этот исходный скилл интерактивен. Убедитесь, что репозиторий и доска GitHub Project действительно ваши. Автоматическое добавление новых issues в доску требует отдельной настройки workflow проекта или добавления issues вручную.
5. Начните новый чат/сессию агента после копирования. Скиллы расположены в `.agents/skills`; для локального Claude Code есть обёртки в `.claude/skills`, которые читают те же исходные файлы. Если другие глобальные скиллы или плагины с теми же названиями имеют приоритет, выберите проектную версию. Облачные окружения имеют собственные правила обнаружения и авторизации — проверьте это в конкретном инструменте.
6. Зафиксируйте и отправьте `.agents/team.json` и workflow в **основную ветку**, включите GitHub Actions и разрешите `GITHUB_TOKEN` запись issues. Без настоящего файла команды workflow ничего не меняет.

## Как работает основной процесс

`/grill-with-docs` → `/to-spec` → `/to-tickets` → `/implement` → `/code-review` → `/retro`.

`/to-tickets` нарезает работу на **срезы** — поведение, которое можно показать целиком. Каждый срез делится на **тикеты**, по одному на роль. Если тикетов в срезе несколько, у среза появляются:

- родительский issue с **контрактом** (как части стыкуются: API, форматы данных) и критериями приёмки; тикеты среза делаются параллельно по этому контракту;
- **тикет проверки** без роли: соединяет части и проверяет срез целиком.

Решение и его причины описаны в `docs/adr/0001-role-tickets-within-slices.md`. Разбиение агент показывает по срезам: роль, оценка и блокеры каждого тикета. После согласования он публикует issues с меткой `ready-for-agent` и метаданными распределения, затем запускает предпросмотр и сообщает, кому что досталось. Если команда, `gh`, права или целевой репозиторий не настроены, агент сообщает, что нужно исправить, и не выдумывает назначения.

Владельцев назначает workflow **Distribute tickets**. Он запускается, когда issue с меткой `ready-for-agent` создают, помечают или снимают с него владельца, при изменении `.agents/team.json` в основной ветке и вручную. Распределитель назначает **реальных людей** и не запускает за них Codex/Cursor/Claude Code:

- тикет получает участник с нужной ролью и наименьшей нагрузкой относительно `capacity`; тикет без роли может получить любой;
- тикет проверки получает наименее загруженный владелец одной из частей среза;
- тикет, у которого уже есть владелец, никогда не меняется;
- если роли нет ни у одного участника, тикет остаётся без владельца, а причина видна в логе workflow.

Заблокированный тикет получает владельца сразу, но начинать его можно только после закрытия блокеров. Issues без метаданных, например старые, пропускаются. Подробные правила и формат: `.agents/workflow/distribution.md`.

**Передача тикета:** снимите владельца в GitHub, и workflow назначит нового. Если участник уходит из команды, сначала удалите его из `.agents/team.json`, иначе тикет может вернуться к нему. Чтобы выбрать нового владельца самостоятельно, сначала добавьте его, потом снимите прежнего. Передача не переносит ветку, не останавливает агента и не запускает другого: новый владелец проверяет незаконченный PR и договаривается о передаче работы.

Участник открывает свой тикет в любимом инструменте и работает в отдельной ветке и рабочем каталоге/worktree. В PR указывайте `Closes #номер` для соответствующего тикета. Ответственный проверяет PR и интеграцию.

**Закрытие родительских issues.** Когда закрывается последний sub-issue, workflow **Close finished parents** закрывает родительский issue, а затем, по той же логике, и его родителя. Последний тикет среза закрывает срез, последний срез закрывает спеку. Карты `/wayfinder` (метка `wayfinder:map`) и issues других репозиториев workflow не трогает. Если PR реализует issue напрямую, без тикетов, укажите `Closes #номер` этого issue. При смене состава команды вручную обновляйте `.agents/team.json`; это не автоматическая синхронизация с организацией GitHub.

## Проверка

Из корня шаблона:

```shell
python -m unittest discover -s tests -v
```

В рабочем проекте с настроенным `.agents/team.json` можно посмотреть план распределения, ничего не меняя:

```shell
python .agents/workflow/distribute.py --team .agents/team.json
```

С `--apply` скрипт записывает назначения, но пока включён workflow, не запускайте его так локально: у локального запуска и Actions нет общей блокировки.
