# Шаблон: GitHub Projects + агенты

Это шаблон для GitHub-репозитория: 27 скиллов Matt Pocock в `.agents/skills`, общие инструкции и распределитель GitHub Issues с учётом доступности команды. Поддерживаются Codex, Cursor и Claude Code. В исходном шаблоне нет состава команды и действующего расписания.

## Как перенести

1. Создайте репозиторий из этого шаблона или скопируйте в существующий `.agents/`, `.claude/`, `.github/workflows/availability-reconcile.yml`, `AGENTS.md` и `CLAUDE.md`. При желании добавьте `tests/`. Если файлы уже есть, сначала объедините их, сохранив существующие инструкции и настройки.
2. На компьютере, где выполняется распределение, нужны Python 3 и установленный GitHub CLI (`gh`). Выполните `gh auth login`; у аккаунта должны быть права читать issues и назначать участников. Подключение агентов к GitHub само по себе не заменяет `gh` для этого распределителя.
3. Скопируйте `.agents/team.example.json` в `.agents/team.json`. Укажите настоящий `OWNER/REPOSITORY`, GitHub-логины участников, относительную `capacity` и `skills`. Участник по умолчанию `away`. `general` — обычный навык, не универсальная маска. Не добавляйте токены в JSON. Каждый участник должен иметь право быть назначенным на issue в этом репозитории.
4. Откройте репозиторий в своём агенте и выполните `/setup-matt-pocock-skills`: выберите GitHub Issues и настройте документацию трекера и метки. Этот исходный скилл интерактивен. Убедитесь, что репозиторий и доска GitHub Project действительно ваши. Автоматическое добавление новых issues в доску требует отдельной настройки workflow проекта или добавления issues вручную.
5. Начните новый чат/сессию агента после копирования. Скиллы расположены в `.agents/skills`; для локального Claude Code есть обёртки в `.claude/skills`, которые читают те же исходные файлы. Если другие глобальные скиллы или плагины с теми же названиями имеют приоритет, выберите проектную версию. Облачные окружения имеют собственные правила обнаружения и авторизации — проверьте это в конкретном инструменте.

6. Зафиксируйте и отправьте `.agents/team.json` и workflow в **основную ветку**, включите GitHub Actions и проверьте, что у `GITHUB_TOKEN` есть права `issues: write`. Без настоящего файла команды workflow ничего не меняет. GitHub Projects настраивается отдельно; доска не является источником отметок присутствия.

## Как работает основной процесс

`/grill-with-docs` → `/to-spec` → `/to-tickets` → `/implement` → `/code-review` → `/retro`.

Исходный `/to-tickets` сначала предлагает декомпозицию и спрашивает о ней. После согласования он создаёт issues, затем дополнительный шаг собирает манифест и запускает распределитель с `--apply`. Если команда, `gh`, права или целевой репозиторий не настроены, агент сообщает, что нужно исправить, и не выдумывает назначения. Повторного подтверждения каждого назначения в инструкции нет; политика конкретной среды может требовать разрешение на действия.

Распределитель назначает **реальных людей**, не запускает за них Codex/Cursor/Claude Code. Он учитывает навыки, `capacity`, оценки, зависимости и действующие отметки присутствия. Если единственный владелец задачи явно ушёл или его смена закончилась, задача передаётся работающему подходящему участнику. Если замены нет, прежний владелец сохраняется; новая задача остаётся без назначения. Если присутствие владельца неизвестно, он не считается доступным, но его задачи автоматически не отбираются. Множественные и внешние назначения не меняются. Заблокированную задачу нельзя начинать, пока её блокеры не закрыты.

### Отметка начала и окончания смены

В начале работы участник ставит отметку с длительностью смены. Команда сама сохранит время окончания в UTC:

```shell
python .agents/workflow/availability.py --team .agents/team.json --login GITHUB_LOGIN --hours 8
```

Если уходит раньше, он отмечает это явно:

```shell
python .agents/workflow/availability.py --team .agents/team.json --login GITHUB_LOGIN --away
```

После каждой отметки нужно **закоммитить и отправить `.agents/team.json` в основную ветку**: локальный файл другие участники и GitHub Actions не видят. При push workflow проверяет задачи; окончание смены без отдельной отметки проверяется по расписанию примерно каждые 10 минут. Запуск может задержаться на стороне GitHub. Новая смена требует новой отметки.

Обработка охватывает открытые issues с меткой `ready-for-agent` и корректными метаданными `agent-distribution` в описании: проектный `/to-tickets` должен добавлять их при публикации. Старые issues без метаданных пропускаются. Посмотреть результат и причины пропуска можно в логах workflow **Reconcile issue owners**. Подробные правила и формат: `.agents/workflow/distribution.md`.

Передача issue не переносит ветку, не останавливает агента и не запускает другого. Новый владелец должен проверить незаконченный PR и договориться о передаче работы. Два одновременно работающих распределителя могут конфликтовать: планировщик Actions сериализован, но ручной локальный запуск с ним общей блокировки не имеет.

Участник открывает свою issue в любимом инструменте и работает в отдельной ветке и рабочем каталоге/worktree. В PR указывайте `Closes #номер` для соответствующей задачи. Ответственный проверяет PR и интеграцию. При смене состава команды вручную обновляйте `.agents/team.json`; это не автоматическая синхронизация с организацией GitHub.

## Проверка без GitHub

Из корня шаблона:

```shell
python .agents/workflow/distribute.py --team .agents/workflow/demo/team.json --tickets .agents/workflow/demo/tickets.json --snapshot .agents/workflow/demo/snapshot.json
python -m unittest discover -s tests -v
```

Первая команда только печатает план для вымышленных людей и issues. `--snapshot` нельзя совместить с `--apply`. В рабочем проекте распределение выполняется через `gh` и реальный манифест, как описано в `.agents/workflow/distribution.md`.
